1. Purpose, method, and an honesty statement

This page compares Morbstack against six things developers actually reach for on macOS: Docker Desktop, OrbStack, Podman Desktop (+ podman machine), Rancher Desktop, Colima (+ Lima), and Apple's open-source container project. It exists to answer, as precisely as the evidence allows, "how does Morbstack actually differ, and where is it actually worse."

Evidence tiers, and what each is worth

  • Morbstack's own numbers come from exactly four places in this repository — parity.md, roadmap.md, compat.md, and amd64.md/k8s.md — and nowhere else. No number about Morbstack below was generated for this page. Where a figure is a target rather than a measurement, it is labeled as such every time it appears.
  • Local, first-hand inspection covers Docker Desktop, which was installed on the machine this document was written on (bundle timestamps dated December 2024 — an older installed copy, not necessarily the current shipping release). It was inspected read-only: bundle contents, codesign, otool, nm, and a snapshot of already-running processes, nothing started, stopped, or reconfigured. OrbStack, Podman, Rancher Desktop, Colima, and Apple's container are not installed on that machine — every claim about them below is web-sourced, not independently reproduced, and marked accordingly.
  • Vendor and third-party claims from the web are quoted and attributed, never presented as Morbstack-verified fact.
  • Anywhere research was inconclusive, this document says "could not verify" rather than filling the gap from memory.
The honesty statement this page is built to satisfy

Morbstack is pre-alpha, unreleased, and has never been used by anyone outside this repository's own test passes. It has one maintainer, no security audit, no notarized installer, and — per its own parity audit — 6 outright failures and 3 behavioral gaps out of 29 real drop-in-compatibility checks run against a live build. Every competitor discussed here has shipped, has real users, and in most cases has been hardened by exactly the kind of adversarial and edge-case usage Morbstack has not yet received. Where this page argues Morbstack has a structural advantage (license, VM topology, native UI), that advantage is real and evidenced below — but it is an advantage of design, not of maturity, and §6 exists specifically to keep those two things from blurring together.

Reading this table honestly: Morbstack, Docker Desktop, OrbStack, Podman machine, Rancher Desktop, and Colima all converge on the same basic shape — one shared Linux VM, Virtualization.framework (or Lima's abstraction over it) as the hypervisor, VirtioFS-family bind mounts. Morbstack's specific bet inside that shape is being the only one of the six with zero modification to the actual container engine verified end-to-end (parity.md #1-#4, #12-#14) — Podman and Apple's container aren't running Docker's engine at all, and OrbStack's engine internals are unverifiable because the product is closed source. Apple's container is architecturally the odd one out entirely: per-container micro-VMs trade away exactly the shared-kernel properties (Compose networks, --network container:x, shared page cache) that architecture.md explains Morbstack deliberately kept a single shared VM to preserve.

Morbstack, Podman Desktop, Rancher Desktop, Colima, and Apple's container are all genuinely free-forever open source with no commercial trigger — on licensing terms alone, Morbstack is tied with four established projects, not uniquely differentiated from all of them. Its real differentiation is narrower: it is the only one of the six simultaneously (a) free with no commercial-use asterisk, (b) built around unmodified, off-the-shelf upstream dockerd/containerd — no downstream engine patch, published ports made reachable by a small Morbstack userland proxy that dockerd execs through its own --userland-proxy-path flag — rather than a different or closed engine, and (c) aimed at drop-in Docker Desktop replacement rather than a CLI-only tool or a different API surface entirely. Whether it achieves that combination today is a feature-completeness and quality question, covered honestly in §5 and §6.

5. Performance: claims vs. measured reality

Kept in three explicitly separate buckets, because blurring them is the single easiest way to lose a skeptical reader's trust.

(a) Vendor claims — quoted and attributed, not verified here

  • OrbStack states, on its own comparison page, "fast startup," "low CPU usage," "low power usage," and "memory on demand" relative to Docker Desktop — presented as a checkmark comparison, not first-party numbers on that page itself (OrbStack vs. Docker Desktop). Third-party writeups report ~2s OrbStack startup vs. 20-30s for Docker Desktop, and roughly 200MB vs. 4GB idle memory — third-party numbers, not independently reproduced here (sliplane.io comparison).
  • Apple's container claims its per-container VMs achieve "sub-second startup times through careful kernel optimization," per third-party technical summaries — could not independently verify the underlying Apple source.
  • No performance claims from Podman Desktop, Rancher Desktop, or Colima were found stated as vendor marketing in this research pass.

(b) Morbstack's own measured numbers — with conditions, not marketing

Real, timed, end-to-end runs on one development machine, Apple silicon — from architecture.md, parity.md, amd64.md, and k8s.md — not the CI-gated morb bench numbers for M2+.

  • Cold, socket-activated docker run --rm hello-world: 2.09s wall clock, guest MRB0 control socket ready 1.69-2.01s after VM bring-up.
  • morb stop: 0.25-0.40s. A subsequent cold boot to a responsive docker ps: 1.69-1.73s, repeatable with zero ERROR/WARN log lines.
  • First-boot disk formatting (mkfs.ext4): 22ms; mount 56ms after that; a real alpine registry pull: 1.95s.
  • Idle-auto-suspend cycle: guest powered off in 384ms after the idle timer fired; next socket-activated command woke a fresh VM in 2.13s. This is a graceful stop, not a true suspend-to-zero snapshot/restore — Virtualization.framework's restoreMachineStateFrom does not work for Morbstack's direct-kernel-boot guest on this development host, a documented API limitation, not a Morbstack bug.
  • amd64-via-Rosetta slowdown, same guest and session: no measurable container-start penalty; general-purpose compute ~1.8-2x slower; SHA-256 at 16KB blocks ~5.1x slower; RSA-2048 sign ~3.8x slower, verify ~2.3x slower.
  • Kubernetes (morb k8s): cold enable-to-Ready 8.3s with a full payload transfer; ~4s on a subsequent enable with the payload already present. Idle cost with the cluster on and nothing deployed: guest memory rose from ~137MB to ~617MB, host VM-process CPU rose from ~0.7% to ~20-23%.

(c) Morbstack's published targets — not yet measured, do not read as results

docs/roadmap.md's public performance target table commits Morbstack to publishing accurate status against these from M2 onward via morb bench — goals the project is answerable to, explicitly not claims about the current build.

Treat the closeness of the boot numbers as encouraging, not as evidence the harder targets are anywhere near proven.

6. Where Morbstack is worse — the honest section

This section is deliberately at least as detailed as §§2-5 combined are flattering. Everything here is either a documented FAIL/PARTIAL from the real 29-check audit, an explicit not yet built item from the roadmap, an explicit non-goal, or a structural maturity gap that is simply true of a one-maintainer, pre-alpha project regardless of what its docs say.

Things that are broken, absent, or still lack release-grade live evidence

  • The bundled Docker client path has implementation, not clean-machine release proof. The development app bundle contains signed upstream docker, docker compose, and docker buildx. Its explicit first-run transaction places only Morbstack-owned links on PATH, registers a context, and creates the conventional per-user socket only when it is safely absent. That path still needs a clean-profile, real-VM acceptance run before it can be called a drop-in installation guarantee.
  • host.docker.internal and gateway.docker.internal have implementation, pending a fresh VM pass. The guest split-DNS service resolves both aliases to the VM NAT gateway, but the historical failure remains in the parity audit until a fresh run proves both resolution and a real connection to a Mac-side listener.
  • Zero-config discovery is deliberately consented and still needs clean-profile evidence. After reviewed setup, Morbstack creates ~/.docker/run/docker.sock only when it is safe to own and registers its Docker context without overwriting another current context. Testcontainers, IDEs, and docker-py need a fresh clean-machine acceptance pass before this is promoted from implementation to release claim.
  • Buildx is bundled and wired by reviewed setup, pending clean-profile evidence. The app packages the unmodified upstream Buildx plugin and the first-run transaction links it in Docker's standard plugin location. The native Builds workflow invokes that bundled tool explicitly; a clean-machine BuildKit run is still a release gate.
  • The historical bare-/tmp bind-mount corruption is repaired in source, pending VM revalidation. The default /private/tmp share aliases /tmp in the guest, and unsafe unresolved paths are rejected before Docker receives a misleading mount request. Custom shares can still make /tmp unavailable, so this must remain an explicit error rather than a false success.
  • No inotify across VirtioFS bind mounts, confirmed directly. A host-side file edit is correct the instant it's read, but the change-notification event a hot-reload watcher depends on never crosses the boundary — confirmed with a live nodemon test that produced zero restarts after an 8-second wait. The working mitigation (polling) exists and was verified, but it is a workaround, not a fix.
  • Fixed, non-negotiable bind-mount ownership. Every file inside a VirtioFS bind mount shows up as root:root in the guest regardless of which host user owns it, and a container-side chown against it is silently accepted and silently discarded.
  • Published-port handling is intentionally bounded. Fixed loopback TCP ports reserve a real Mac listener before Docker create and activate forwarding only after the exact start success response. Dynamic TCP allocation has a constrained standard-request path; opaque, ranged, non-loopback, and nonstandard request forms do not claim the same synchronous guarantee. VM-stop recovery remains in progress.
  • UDP forwarding is real but has a narrower guarantee. The loopback datagram relay preserves request/reply boundaries once Docker reports a concrete port. Dynamic or ranged UDP publishes deliberately do not claim TCP-style pre-start reservation.
  • No qemu fallback for amd64, despite the plumbing existing — no static qemu-x86_64 ships, so anything Rosetta cannot translate simply fails with no fallback.
  • No *.morb.local DNS, no morbnet, no host-routable container IPs, no split-DNS. Containers get outbound NAT and nothing else today.
  • No synced-share filesystem tier. VirtioFS (tier 1) is the only option; the opt-in synced-copy mode does not exist yet.

Things competitors have that Morbstack has chosen never to build

Per the explicit non-goals in docs/compat.md — stated up front so readers don't mistake them for gaps that will eventually close:

  • Windows containers — never supported, at any milestone. Docker Desktop on Windows hosts supports this, and it is a real category some users need.
  • CUDA/GPU passthrough — not supported, no commitment to add it. Colima has a krunkit VM type specifically for this; Docker Desktop has GPU support on some platforms.
  • Docker Desktop Extensions compatibility — explicitly not a target. Docker Desktop, Podman Desktop, and Rancher Desktop all have some form of extension ecosystem today; Morbstack's native (non-web-view) plugin SDK is a post-1.0 idea, not a compatibility shim.
  • CRIU (checkpoint/restore) — off, not a target for 1.0 or the 1.x line as currently scoped.

Maturity gaps that are just true, regardless of documentation quality

  • Pre-alpha, unreleased, no version number a user could install today. Every other product here has a real release channel; a reader cannot brew install morbstack right now.
  • One maintainer. Podman Desktop (Red Hat/CNCF), Rancher Desktop (SUSE), Colima (long-running community), Apple's container (Apple) all have an organization or sustained community behind them. Morbstack does not yet.
  • No independent security audit. Explicitly a 1.0 gate, not done yet.
  • No notarized, signed release build; no installer. Building from source with Xcode 26+ and a Rust cross-toolchain is the only way to run it today.
  • Effectively zero user base outside this repository's own test passes. No production usage, no bug reports from anyone who wasn't already working on the project.
  • VM suspend/resume is not actually implemented as suspend/resume. morb suspend degrades to a graceful stop plus a cold boot on next use. The public "≤500ms resume" target has nothing behind it yet.
  • No public compat-matrix CI. Everything in this document about Morbstack's ecosystem compatibility rests on one manual audit pass, not continuous verification.

Anyone reading this page and concluding "Morbstack is strictly better" has not read it carefully enough — that conclusion isn't supported by the project's own documentation, and this section exists so it doesn't need to be argued with.

7. Who should use what

A recommendation section that doesn't send every reader to Morbstack is the only kind worth writing.

Use Docker Desktop if:
you need Windows container support, GPU passthrough that's actually documented and supported, Docker Desktop Extensions, or you're inside an organization already paying for it and the $9-24/user/month is a non-issue. It is also, simply, the thing with the largest install base and the least chance of a workflow-specific surprise.
Use OrbStack if:
you're under the $10k/yr or personal-use threshold, want a closed-source but reportedly fast and well-integrated native experience today, and don't need the source to be inspectable or the product free at any company size.
Use Podman Desktop + podman machine if:
you specifically want a daemonless/rootless model, need Kubernetes-native tooling, or your organization has policy reasons to avoid a Docker-Engine-shaped daemon — accepting you're not running the actual Docker Engine, only something CLI-compatible with it.
Use Rancher Desktop if:
Kubernetes is the primary workload, not an afterthought, and you want first-class containerd/nerdctl alongside Moby with a choice between them.
Use Colima (+ Lima) if:
you don't want or need a GUI at all, you're comfortable at the command line, and you want the lightest possible free and open-source Docker-API-compatible VM with maximum backend flexibility.
Use Apple's container if:
per-container VM-grade isolation matters more to you than Docker ecosystem compatibility, you're on macOS 26 with Apple silicon, and you're comfortable with a CLI that doesn't speak the Docker API and has no Compose story today.
Use Morbstack if:
you want a free-forever, Apache-2.0, source-visible Docker Desktop replacement built around an unmodified upstream Docker Engine (published ports served through dockerd's own stock --userland-proxy-path hook, not an engine patch) — and you are comfortable being an early adopter of pre-alpha software with one maintainer, no security audit, missing host.docker.internal/zero-config discovery/buildx-out-of-the-box, and the specific /tmp bind-mount and inotify gotchas documented above. If any of those gaps would break your actual workflow today, use one of the other six until Morbstack's roadmap closes them.
