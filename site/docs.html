Getting started

Prerequisites

Apple silicon, macOS 15 (Sequoia) or later to run it, Xcode 26 or later to build it (Swift 6.3, Virtualization.framework). See system requirements for the full detail and citations.

Build and first run

The full, real build-from-source walkthrough — clone, mise trust && mise install, mise run build, fetching guest assets, assembling the guest image, and starting the daemon — lives on the Download page, since there is no packaged build to fetch instead. It ends with:

mise run run-daemon
# in another terminal:
export DOCKER_HOST=unix://$HOME/.morbstack/run/docker.sock
docker run --rm hello-world

Connecting the Docker CLI

Morbstack does not register a Docker context or take over the conventional socket path automatically (that's tracked as a gap, not an oversight — see docs/compat.md). Note also that Morbstack does not install a docker client itself today — the commands below assume one is already on your PATH; shipping a bundled, hash-verified client is the "single-path install" gate tracked for the first public release (docs/roadmap.md, L1). Point whatever stock docker client you have at it one of two ways:

# one-off, per shell session
export DOCKER_HOST=unix://$HOME/.morbstack/run/docker.sock

# or persistent, via a docker context
docker context create morbstack --docker host=unix://$HOME/.morbstack/run/docker.sock
docker context use morbstack

The CLI also has its own context helper: morb context status / create / use — see the CLI reference below. morb context use always asks before changing your default context, and refuses to replace an existing explicit default without --force.

The Compose plugin

Fetched and hash-verified by scripts/fetch-guest-assets.sh, but not installed into ~/.docker/cli-plugins automatically:

mkdir -p ~/.docker/cli-plugins
ln -sf "$(pwd)/dist/host-bin/docker-compose" ~/.docker/cli-plugins/docker-compose
docker compose version

Or use morb install-cli-plugins, which symlinks whatever plugin binaries it finds next to the CLI or under dist/host-bin — it always prints its plan and asks first unless --force is passed.

Global options

--json
Emit raw JSON instead of human-readable output.
--force
Skip Morbstack's confirmation prompt (reset-disk, context create, install-cli-plugins), replace another explicit default context (context use), or stop the VM without asking the guest first (stop). Deliberately refused by rosetta install — that installs system software under Apple's licence, so it always asks the person at the keyboard.
--print-plan

--help
Print the full usage text.

Compatibility

The contract

From docs/compat.md — the compatibility contract Morbstack commits to, so "does my existing workflow keep working" has a precise answer:

  • Unmodified docker CLI. Any stock docker binary works against Morbstack's relayed Engine API — no patched client, ever.
  • Docker contexts are respected, never stomped. Morbstack adds itself as a context; it never silently rewrites your existing default.
  • Engine API = upstream moby, verbatim. No added, removed, or reshaped endpoints — whatever the bundled dockerd version exposes is what you get.
  • Compose v2 and buildx are bundled, from M1 onward. As of today, Compose already works end-to-end with a one-time manual plugin symlink; buildx is not fetched or tested yet at any milestone so far.
  • ~/.docker/config.json is honored — credential helpers, the macOS keychain helper, and registry mirrors, the same way stock Docker tooling reads it.

Explicit non-goals

Stated up front so they are not mistaken for gaps to be filled later — from docs/compat.md:

  • Windows containers. Never supported — Morbstack targets Linux containers only.
  • CRIU (checkpoint/restore). Off, not a target for 1.0 or the 1.x line as currently scoped.
  • CUDA / GPU passthrough. Not supported, no commitment to add it.
  • Docker Desktop Extensions. Not supported and not planned — Extensions are web-view based, which conflicts with Morbstack's zero-web-view host integration principle. A native plugin SDK is a post-1.0 idea, not a compatibility shim for existing Extensions.

Troubleshooting

docker pull/docker run hangs with no output for minutes

Run morb doctor. This is very likely the docker-credentials check: Docker Desktop writes "credsStore": "desktop" into ~/.docker/config.json, and the standard docker CLI shells out to docker-credential-desktop for every registry auth lookup — which only answers while Docker Desktop itself is running. With Desktop absent, the CLI hangs waiting on a process that never answers. Fix: remove the credsStore line from ~/.docker/config.json, or point DOCKER_CONFIG at a directory with a config that omits it. Morbstack never edits that file for you.

My bind mount is empty, or a single-file mount reads as a directory

Run morb shares. A current Engine request canonicalizes macOS /tmp to /private/tmp, checks the configured share that is actually mounted in the guest, and rejects unshared, missing explicit, or symlink-escaping bind sources with a Docker error before forwarding. The old silent-empty-directory behavior is retained only as historical audit evidence.

My dev server's hot reload doesn't fire on a host-side edit

VirtioFS bind mounts don't forward inotify events across the host/guest boundary — a file is correct the instant you read it, but the change-notification event a watcher (nodemon, webpack --watch, vite) depends on never arrives. The working mitigation is a polling watcher: nodemon --legacy-watch (or your tool's equivalent) picks up changes correctly. There is no fix short of polling today.

A published port answers nothing, and docker ps insists it's published

For an ordinary fixed loopback TCP publication, Morbstack now holds the host listener before create and returns a Docker-style conflict before the container is reported running. Dynamic/range ports, unsupported request framing, and VM-stop recovery have their own explicit capability boundaries; Morbstack must reject or diagnose them rather than show a successful-looking unreachable port.
